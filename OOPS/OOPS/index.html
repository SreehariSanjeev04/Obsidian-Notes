    • 1. What OOP Solves

    C++ OOP Interview Guide

    This guide covers the C++ OOP concepts most useful for a Ribbon Communications-style C/C++ systems interview, including implementation-oriented questions.

    1. What OOP Solves

    Object-oriented programming groups state and the operations on that state into objects.

    Without OOP:

    struct Router {
    std::string name;
    int ports;
};

void startRouter(Router* r);
void stopRouter(Router* r);

    With OOP:

    class Router {
private:
    std::string name;
    int ports;

public:
    void start();
    void stop();
};

    The four classic pillars:

    Encapsulation
Abstraction
Inheritance
Polymorphism

    2. Class and Object

    A class is a blueprint.
    An object is an instance of a class.

    class Router {
public:
    std::string name;
    int ports;

    void printInfo() {
        std::cout << name << " " << ports << '\n';
    }
    friend class MyClassB;
};

int main() {
    Router r1;

    r1.name = "R1";
    r1.ports = 48;

    r1.printInfo();
}

    Router → class
r1     → object

    3. Access Specifiers

    C++ has:

    public
private
protected

    public

    Accessible from outside the class.

    class A {
public:
    int x;
};

A a;
a.x = 10;

    private

    Accessible only from inside the class and friends.

    class A {
private:
    int x;
};

    This is invalid:

    A a;
a.x = 10;

    protected

    Accessible inside the class and derived classes, but not normally from outside.

    4. Encapsulation

    Encapsulation means bundling data and behavior while controlling access to internal state.

    Bad:

    class BankAccount {
public:
    double balance;
};

    Better:

    class BankAccount {
private:
    double balance;

public:
    void deposit(double amount) {
        if (amount > 0)
            balance += amount;
    }

    bool withdraw(double amount) {
        if (amount <= 0 || amount > balance)
            return false;

        balance -= amount;
        return true;
    }

    double getBalance() const {
        return balance;
    }
};

    Interview definition

    Encapsulation bundles data and the methods that operate on it, while restricting direct access to the object's internal state.

    5. Abstraction

    Abstraction means exposing what an object does while hiding unnecessary implementation details.

    class NetworkInterface {
public:
    void sendPacket() {
        // complicated implementation
    }
};

    The caller only needs:

    interface.sendPacket();

    They don't need to know about:

    • DMA
    • buffers
    • NIC registers
    • interrupts
    • checksums

    Encapsulation vs Abstraction

    A useful distinction:

    Encapsulation → Who can touch this?
Abstraction   → What do I need to know?

    6. Constructors

    A constructor initializes an object.

    class Router {
private:
    std::string name;
    int ports;

public:
    Router(std::string n, int p)
        : name(n), ports(p) {}
};

    Usage:

    Router r("R1", 48);

    Initializer Lists

    Prefer:

    Router(std::string n, int p)
    : name(n), ports(p)
{
}

    over:

    Router(std::string n, int p) {
    name = n;
    ports = p;
}

    Initializer lists are important for:

    • const members
    • reference members
    • base classes
    • direct construction of member objects

    Example:

    class A {
    const int x;

public:
    A(int n) : x(n) {}
};

    7. Types of Constructors

    Default constructor

    class A {
public:
    A() {
        std::cout << "Constructor\n";
    }
};

A obj;

    Parameterized constructor

    A(int x) {
    // ...
}

    A obj(10);

    Constructor overloading

    class Router {
public:
    Router() {}

    Router(std::string name) {}

    Router(std::string name, int ports) {}
};

    This is compile-time polymorphism through overloading.

    8. Destructor

    A destructor runs when an object is destroyed.

    class A {
public:
    ~A() {
        std::cout << "Destroyed\n";
    }
};

    A common use is releasing resources.

    class Buffer {
    int* data;

public:
    Buffer(int size) {
        data = new int[size];
    }

    ~Buffer() {
        delete[] data;
    }
};

    This naturally leads to copy semantics and RAII.

    9. this Pointer

    Inside a member function, this points to the current object.

    class A {
    int x;

public:
    A(int x) {
        this->x = x;
    }
};

    Conceptually:

    this → current object

    10. Static Members

    A static data member is shared by all objects of the class.

    class Router {
public:
    static int count;

    Router() {
        count++;
    }
};

int Router::count = 0;

    Router a;
Router b;

std::cout << Router::count;  // 2

    There is only one count, not one per object.

    11. Inheritance

    Inheritance lets a derived class reuse or extend a base class.

    class Device {
public:
    void powerOn() {
        std::cout << "Power on\n";
    }
};

class Router : public Device {
};

    Router r;
r.powerOn();

    Conceptually:

    Device
  ↑
Router

    12. Types of Inheritance

    Single inheritance

    A
↑
B

    Multilevel inheritance

    A
↑
B
↑
C

    Multiple inheritance

    A     B
 \   /
   C

    Hierarchical inheritance

          A
    /   \
   B     C

    Hybrid inheritance

    A combination of multiple inheritance structures.

    13. Public / Protected / Private Inheritance

    For:

    class B : public A {};

    the usual mapping is:

    Base member In derived class
    public public
    protected protected
    private inaccessible

    For protected inheritance:

    Base member In derived class
    public protected
    protected protected
    private inaccessible

    For private inheritance:

    Base member In derived class
    public private
    protected private
    private inaccessible

    In design questions, public inheritance normally represents an is-a relationship.

    14. Is-A vs Has-A

    Is-A → inheritance

    Dog IS-A Animal
Router IS-A NetworkDevice

    Has-A → composition

    Router HAS-A CPU
Router HAS-A NetworkInterface
Car HAS-A Engine

    Example:

    class CPU {
public:
    void start() {}
};

class Router {
private:
    CPU cpu;

public:
    void boot() {
        cpu.start();
    }
};

    15. Composition

    Composition means one object contains another object.

    class CPU {};

class Router {
private:
    CPU cpu;
};

    The Router has a CPU.

    For object-oriented design, prefer composition when the relationship is naturally "has-a" rather than forcing inheritance.

    16. Association vs Aggregation vs Composition

    Association

    Objects know or use each other.

    Teacher ---- Student

    Aggregation

    A whole contains objects that can exist independently.

    Team ---- Player

    A player can exist without the team.

    Composition

    Strong ownership/lifetime relationship.

    House ---- Room

    The distinction is most useful when discussing object lifetime and ownership.

    17. Polymorphism

    Polymorphism means one interface can represent multiple implementations.

    Two broad forms:

    Compile-time polymorphism
Runtime polymorphism

    18. Compile-Time Polymorphism

    Function overloading

    void print(int x);
void print(double x);
void print(const std::string& x);

    The compiler determines which function to call.

    Operator overloading

    class Complex {
public:
    Complex operator+(const Complex& other);
};

    Then:

    c3 = c1 + c2;

    19. Runtime Polymorphism

    Runtime polymorphism is commonly implemented with virtual functions.

    class Device {
public:
    virtual void start() {
        std::cout << "Device start\n";
    }
};

class Router : public Device {
public:
    void start() override {
        std::cout << "Router start\n";
    }
};

    Then:

    Device* d = new Router();
d->start();
delete d;

    With virtual, Router::start() is selected.

    20. Why virtual?

    Without virtual:

    class Device {
public:
    void start() {
        std::cout << "Device\n";
    }
};

class Router : public Device {
public:
    void start() {
        std::cout << "Router\n";
    }
};

Device* d = new Router();
d->start();

    This calls:

    Device

    With virtual, the derived implementation is selected through dynamic dispatch.

    21. Virtual Function Internals

    A common implementation model uses a vtable.

    Conceptually:

    Router object
     |
     ↓
   vptr
     |
     ↓
  vtable
  ├── start()
  ├── stop()
  └── configure()

    Then:

    Device* d = new Router();
d->start();

    uses the object's dynamic type to select the appropriate function.

    Important: the C++ standard specifies the behavior, not a requirement to implement it using a vtable. A vtable is the common implementation technique.

    22. Function Overloading vs Function Overriding

    Overloading

    Same function name, different parameter list.

    foo(int);
foo(double);

    Usually occurs within the same class.

    Overriding

    A derived class supplies a new implementation for a virtual function from the base class.

    class A {
public:
    virtual void foo() {}
};

class B : public A {
public:
    void foo() override {}
};

    23. override

    Use override when overriding a virtual function:

    void foo() override;

    It tells the compiler that you intend to override a base function and allows the compiler to catch mistakes.

    24. Pure Virtual Function

    A pure virtual function is declared:

    virtual void start() = 0;

    Example:

    class Device {
public:
    virtual void start() = 0;
};

    Derived classes must implement it to become concrete.

    25. Abstract Class

    A class with at least one pure virtual function is abstract.

    class Shape {
public:
    virtual double area() = 0;
};

    This is invalid:

    Shape s;

    But this is valid:

    class Circle : public Shape {
public:
    double area() override {
        return 3.14159;
    }
};

Circle c;
Shape* p = &c;

    26. Interface in C++

    C++ has no interface keyword like Java.

    An interface-like class can be created using pure virtual functions:

    class NetworkDevice {
public:
    virtual void start() = 0;
    virtual void stop() = 0;
    virtual void configure() = 0;

    virtual ~NetworkDevice() = default;
};

    This exposes an abstract contract without forcing callers to know the implementation.

    27. Virtual Destructor

    This is an important interview question.

    Consider:

    class Base {
public:
    ~Base() {}
};

class Derived : public Base {
public:
    ~Derived() {
        std::cout << "Derived destroyed\n";
    }
};

Base* p = new Derived();
delete p;

    If an object can be deleted through a base pointer, the base destructor should generally be virtual:

    class Base {
public:
    virtual ~Base() = default;
};

    Interview rule

    A polymorphic base class should generally have a virtual destructor.

    28. Multiple Inheritance and the Diamond Problem

    Suppose:

           A
      / \
     B   C
      \ /
       D

    If A contains:

    int x;

    then without special handling, D can contain two A subobjects:

    D
├── B → A::x
└── C → A::x

    This creates ambiguity.

    29. Virtual Inheritance

    Use virtual inheritance:

    class B : virtual public A {};
class C : virtual public A {};
class D : public B, public C {};

    Now D contains one shared A subobject.

    Know this for interviews, but prioritize basic inheritance and polymorphism first.

    30. Object Slicing

    Example:

    class Base {
public:
    int a;
};

class Derived : public Base {
public:
    int b;
};

Derived d;
Base b = d;

    The derived portion (b) is sliced away.

    This is object slicing.

    Using a pointer/reference avoids slicing:

    Base* p = &d;
Base& r = d;

    31. Deep Copy vs Shallow Copy

    This is especially important for C++ systems interviews.

    Consider:

    class A {
public:
    int* p;

    A(int x) {
        p = new int(x);
    }
};

    Then:

    A a(10);
A b = a;

    The default copy constructor performs member-wise copying, so both objects may point to the same allocation:

    a.p ─────┐
         ├──> 10
b.p ─────┘

    This is a shallow copy.

    Changing:

    *b.p = 50;

    also changes *a.p.

    It can also lead to double deletion if both objects attempt to free the same resource.

    32. Deep Copy

    Deep copy allocates independent storage:

    class A {
public:
    int* p;

    A(int x) {
        p = new int(x);
    }

    A(const A& other) {
        p = new int(*other.p);
    }

    ~A() {
        delete p;
    }
};

    Now:

    a.p → 10
b.p → 10

    but the pointers refer to different allocations.

    33. Copy Constructor

    A copy constructor initializes a new object from an existing object.

    A b(a);

    or:

    A b = a;

    Typical signature:

    A(const A& other);

    34. Copy Assignment Operator

    Assignment happens when both objects already exist.

    A a;
A b;

b = a;

    You can implement:

    A& operator=(const A& other) {
    if (this != &other) {
        delete p;
        p = new int(*other.p);
    }

    return *this;
}

    The self-assignment check prevents problems with:

    a = a;

    35. Rule of 3

    If a class manually manages a resource and needs one of these:

    destructor
copy constructor
copy assignment operator

    it often needs all three.

    This is the Rule of 3.

    36. Rule of 5

    Modern C++ adds move operations:

    destructor
copy constructor
copy assignment
move constructor
move assignment

    This is the Rule of 5.

    37. Move Semantics

    Copying a large resource can be expensive.

    Instead of copying:

    a → [huge buffer]
b → [copy of huge buffer]

    a move can transfer ownership:

    Before:
a → [huge buffer]
b → nothing

After move:
a → nothing
b → [huge buffer]

    Example:

    class Buffer {
    int* data;

public:
    Buffer(Buffer&& other) noexcept {
        data = other.data;
        other.data = nullptr;
    }
};

    && is an rvalue reference in this context.

    38. Rule of 0

    Modern C++ often avoids manual resource management.

    Instead of raw pointers:

    int* data;

    use RAII-aware types such as:

    std::unique_ptr<int[]> data;

    The idea is:

    Let resource-owning types manage their own lifetime so your class does not need custom destructor/copy/move logic.

    39. Smart Pointers

    unique_ptr

    Single owner:

    auto r = std::make_unique<Router>();

    It cannot normally be copied.

    shared_ptr

    Shared ownership:

    auto a = std::make_shared<Router>();
auto b = a;

    Ownership is reference counted.

    weak_ptr

    Non-owning reference to an object controlled by shared_ptr.

    Useful for avoiding ownership cycles.

    40. RAII

    RAII = Resource Acquisition Is Initialization

    A resource is tied to object lifetime.

    Example:

    class File {
    FILE* f;

public:
    File() {
        f = fopen("x.txt", "r");
    }

    ~File() {
        if (f)
            fclose(f);
    }
};

    Creation → acquire resource.
    Destruction → release resource.

    RAII can manage:

    • memory
    • files
    • sockets
    • locks
    • other system resources

    41. RAII and Mutexes

    Bad:

    mutex.lock();

doSomething();

mutex.unlock();

    A return path or exception could leave the mutex locked.

    Better:

    std::lock_guard<std::mutex> lock(m);
doSomething();

    When lock leaves scope, the mutex is released automatically.

    This is especially useful for systems/concurrency interviews.

    42. References vs Pointers

    Pointer:

    int* p;

    Reference:

    int& r = x;

    Pointer

    • can be null
    • can be reassigned
    • explicit dereference

    Reference

    • must normally bind to an object when initialized
    • cannot be reseated
    • acts as an alias

    43. const

    Understand these:

    const int* p;
int* const p;
const int* const p;

    const int* p

    Pointer to const int.

    You cannot modify the pointed-to integer through p.

    int* const p

    Const pointer to int.

    The pointer cannot point somewhere else, but the integer can be modified.

    const int* const p

    Const pointer to const int.

    Neither can be changed through p.

    44. const Member Functions

    class Router {
public:
    int getPorts() const {
        return ports;
    }
};

    The function promises not to modify the object's observable state.

    This allows:

    const Router r;
r.getPorts();

    when the member function is correctly marked const.

    45. Friends

    A friend function/class can access private or protected members.

    class A {
private:
    int x = 10;

    friend void print(const A&);
};

void print(const A& a) {
    std::cout << a.x;
}

    Know the concept, but do not prioritize it over inheritance, polymorphism, memory management, and RAII.

    46. Templates and Generic Programming

    Basic templates are worth knowing.

    template <typename T>
T add(T a, T b) {
    return a + b;
}

    Usage:

    add<int>(2, 3);
add<double>(2.5, 3.5);

    You should know:

    • function templates
    • class templates
    • basic template use

    Advanced template metaprogramming is low priority for this interview.

    47. Common C++ Interview Traps

    Trap 1: Object slicing

    Derived d;
Base b = d;

    Derived-specific state is lost.

    Trap 2: Virtual vs non-virtual functions

    Know which function is called through a base pointer.

    Trap 3: Missing virtual destructor

    Base* p = new Derived();
delete p;

    If polymorphic deletion is intended, make the base destructor virtual.

    Trap 4: Shallow copying raw pointers

    Two objects can accidentally own the same allocation.

    Trap 5: Returning references to dead objects

    Bad:

    const std::string& getName() {
    return std::string("temporary");
}

    The referenced temporary does not have a valid lifetime for the caller.

    Trap 6: const correctness

    Know where const belongs and why.

    48. OOP Design Principles Worth Knowing

    You do not need deep software-architecture theory, but know these basics.

    Single Responsibility Principle

    A class should have one clear responsibility.

    Bad:

    Router
 ├── routing
 ├── database
 ├── UI
 ├── logging
 └── billing

    Better: split unrelated responsibilities.

    Open/Closed Principle

    Software should generally be open for extension but closed for unnecessary modification.

    Polymorphism often helps.

    Dependency Inversion

    High-level logic should depend on abstractions rather than concrete implementations.

    Example:

    class Device {
public:
    virtual void send() = 0;
    virtual ~Device() = default;
};

    Then higher-level code can use Device* rather than a specific device type.

    49. Implementation Question: Encapsulated Class

    Prompt

    Implement a BankAccount.

    Good solution

    class BankAccount {
private:
    double balance;

public:
    explicit BankAccount(double initial)
        : balance(initial) {}

    void deposit(double amount) {
        if (amount > 0)
            balance += amount;
    }

    bool withdraw(double amount) {
        if (amount <= 0 || amount > balance)
            return false;

        balance -= amount;
        return true;
    }

    double getBalance() const {
        return balance;
    }
};

    Tests:

    • encapsulation
    • constructor
    • validation
    • methods
    • const

    50. Implementation Question: Inheritance + Polymorphism

    Prompt

    51. Implementation Question: Deep Copy

    Prompt

    Create a class containing dynamic memory and implement a proper copy constructor.

    class Buffer {
private:
    int* data;
    size_t size;

public:
    explicit Buffer(size_t n)
        : data(new int[n]{}), size(n) {}

    Buffer(const Buffer& other)
        : data(new int[other.size]),
          size(other.size)
    {
        std::copy(other.data,
                  other.data + size,
                  data);
    }

    ~Buffer() {
        delete[] data;
    }
};

    Then discuss the Rule of 3 and how Rule of 5 would extend the class.

    53. Implementation Question: Thread-Safe Queue

    Very relevant for systems software.

    class ThreadSafeQueue {
private:
    std::queue<int> q;
    mutable std::mutex m;
    std::condition_variable cv;

public:
    void push(int x) {
        {
            std::lock_guard<std::mutex> lock(m);
            q.push(x);
        }

        cv.notify_one();
    }

    int pop() {
        std::unique_lock<std::mutex> lock(m);

        cv.wait(lock, [this] {
            return !q.empty();
        });

        int x = q.front();
        q.pop();

        return x;
    }
};

    This combines:

    C++
OOP
STL
mutex
condition_variable
concurrency
RAII

    54. Implementation Question: Shape Hierarchy

    class Shape {
public:
    virtual double area() const = 0;
    virtual ~Shape() = default;
};

class Circle : public Shape {
private:
    double r;

public:
    explicit Circle(double r)
        : r(r) {}

    double area() const override {
        return 3.141592653589793 * r * r;
    }
};

class Rectangle : public Shape {
private:
    double w;
    double h;

public:
    Rectangle(double w, double h)
        : w(w), h(h) {}

    double area() const override {
        return w * h;
    }
};

    This demonstrates almost every core OOP concept.

    58. What the Interviewer May Ask After You Code

    Do not stop after getting the code to compile.

    Expect questions such as:

    Why virtual?

    Explain runtime polymorphism and dynamic dispatch.

    Why a virtual destructor?

    Because objects may be deleted through a base pointer.

    Why use an abstract class?

    To define a contract while preventing direct instantiation.

    Why composition instead of inheritance?

    Because the relationship is "has-a", not "is-a".

    What happens during a copy?

    Explain copy constructor, shallow vs deep copy, and ownership.

    How do you prevent memory leaks?

    Prefer RAII and smart pointers.

    What happens if two threads call this?

    Discuss race conditions and synchronization.

    How would you extend the design?

    Discuss adding derived classes without modifying stable abstractions.

    60. What to Memorize vs What to Understand

    Memorize the syntax

    class A {};

virtual void foo() = 0;
void foo() override;

virtual ~A() = default;

A(const A&);
A& operator=(const A&);

A(A&&);
A& operator=(A&&);

    Understand deeply

    Why virtual?
Why abstract?
Why virtual destructor?
Why deep copy?
Who owns this memory?
When does an object die?
Is this relationship is-a or has-a?
Can two threads access this simultaneously?
What happens when this object is copied?

    The second list is what separates a memorized candidate from a strong systems-programming candidate.

    OWASP Top 10

    Overview

    The OWASP Top 10 is an awareness document highlighting important security risks in web applications. It helps developers and security professionals understand common vulnerabilities, their causes, impact, and mitigation.

    Key terminology

    • Vulnerability: A weakness in software, design, or configuration.
    • Exploit: A technique that takes advantage of a vulnerability.
    • Impact: The consequence of successful exploitation.
    • Authentication: Verifying who a user is.
    • Authorization: Verifying what a user is allowed to do.
    • Defense in depth: Using multiple layers of security so that one failed control does not compromise the entire system.

    A01 — Broken Access Control

    What it is

    Broken Access Control occurs when a user can perform actions or access resources outside the permissions granted to them.

    Authentication establishes identity; authorization determines permitted actions. A user can be correctly authenticated and still exploit broken access control.

    Common forms

    1. Insecure Direct Object Reference (IDOR)

    An application exposes a resource identifier and fails to check whether the current user is permitted to access that resource.

    Example:

    GET /api/accounts/1001

    If a user changes the identifier to 1002 and the server returns another user's account information, the application has failed to enforce resource-level authorization.

    • Predictable identifiers are not the root cause.
    • UUIDs do not fix missing authorization checks.
    • The server must check permission for the requested resource.

    2. Horizontal privilege escalation

    A user accesses another user’s resources at the same privilege level.

    Example: Alice accesses Bob's profile, order, or account data.

    3. Vertical privilege escalation

    A user obtains capabilities intended for a higher-privileged role.

    Example: A normal user accesses administrative operations.

    4. Client-side authorization

    An application hides buttons or pages from unauthorized users but does not enforce permissions on the backend. An attacker may call the API directly.

    5. Cross-Site Request Forgery (CSRF)

    A browser may automatically attach authentication cookies to a request initiated by a malicious website. If the target application does not adequately validate that the request is legitimate, an unwanted action may be performed using the victim's session.

    Defenses

    • Enforce authorization on the server for every protected request.
    • Deny access by default.
    • Verify resource ownership and permission for each object.
    • Use RBAC (Role-Based Access Control) or ABAC (Attribute-Based Access Control) as appropriate.
    • Do not rely on hidden frontend buttons, URLs, or unguessable IDs.
    • Use CSRF tokens, appropriate SameSite cookie settings and origin validation where applicable.
    • Validate JWT signature, expiration, issuer and audience; do not trust client-modifiable authorization claims.
    • Test endpoints using different roles and ownership contexts.

    Key takeaway: Hiding a button is not authorization. The server must enforce access rules.

    A02 — Security Misconfiguration

    What it is

    Security Misconfiguration occurs when software, infrastructure, servers, cloud services or application components are configured insecurely.

    An application can have secure code but still be vulnerable because of its deployment configuration.

    Common forms

    1. Default credentials

    Leaving default usernames or passwords unchanged can allow unauthorized access to administrative interfaces.

    2. Directory listing

    A web server may expose the contents of directories, potentially revealing backups, configuration files or other sensitive resources.

    3. Debug mode in production

    Debugging features may expose stack traces, internal paths, environment details, framework information or secrets.

    4. Public cloud storage

    Storage buckets or other cloud resources may be configured to allow unintended public access.

    5. Unnecessary services and features

    Unused ports, services, test endpoints, sample applications or administrative interfaces increase the attack surface.

    Defenses

    • Use secure configuration baselines (e.g., CIS Benchmarks where appropriate).
    • Remove or disable unnecessary services, features, accounts and endpoints.
    • Change default credentials.
    • Disable debugging in production.
    • Restrict access to administrative interfaces.
    • Keep databases and internal services off public networks unless necessary.
    • Apply least-privilege cloud IAM policies.
    • Secure HTTP headers, including:
    • Content-Security-Policy (CSP)
    • Strict-Transport-Security (HSTS)
    • X-Content-Type-Options: nosniff
    • frame-ancestors in CSP to control framing and help prevent clickjacking
    • Appropriate Referrer-Policy
    • Use configuration scanning and infrastructure-as-code security checks.
    • Return generic error messages to clients; keep detailed diagnostics in protected logs.

    Key takeaway: Configuration is part of security—not merely deployment or operations.

    A03 — Software Supply Chain Failures

    What it is

    The software supply chain includes the components, tools, processes and systems involved in developing, building, distributing and maintaining software.

    Software Supply Chain Failures arise when weaknesses or malicious activity in these elements compromise software or its delivery.

    Common forms

    1. Vulnerable dependencies

    An application relies on a third-party library with a known vulnerability. The application may be exploitable even when its own code does not contain the vulnerable logic.

    2. Dependency confusion

    An attacker publishes a malicious package using a name that conflicts with an internal package. Poor package-source configuration may cause a build to fetch the attacker-controlled package.

    3. Compromised development tools

    A malicious or compromised IDE extension, compiler, build tool or developer utility may steal secrets, alter code or introduce malicious functionality.

    4. Compromised CI/CD pipeline

    An attacker compromises build or deployment infrastructure and modifies software, artifacts, workflows or credentials.

    Defenses

    • Maintain a Software Bill of Materials (SBOM) listing software components.
    • Scan direct and transitive dependencies for known vulnerabilities.
    • Keep dependencies updated and supported.
    • Use lockfiles and controlled dependency versions.
    • Restrict package sources and use approved repositories.
    • Protect CI/CD systems, workflows and credentials.
    • Use least privilege for developers, build systems and deployment systems.
    • Review code and changes to build workflows.
    • Verify artifact provenance and signatures where available.
    • Monitor dependency and supply-chain security advisories.

    Useful tools include Dependabot, OWASP Dependency-Check, Snyk and Trivy (each has different capabilities and limitations).

    Key takeaway: Trust in your own code is insufficient if the tools, dependencies or build pipeline that produce it are compromised.

    A04 — Cryptographic Failures

    What it is

    Cryptographic Failures occur when sensitive information is not adequately protected due to missing, weak, incorrectly implemented or improperly managed cryptography.

    Common forms

    1. Unencrypted communication

    Sensitive data sent over HTTP may be readable or modifiable by an attacker capable of intercepting the traffic.

    2. Plaintext password storage

    If passwords are stored directly in a database, a database compromise immediately exposes them.

    3. Fast hashes for password storage

    General-purpose hashes such as SHA-256 are too fast for password-storage purposes. Attackers can test guesses at high speed.

    4. Weak algorithms

    Obsolete or inappropriate algorithms can undermine security. MD5 and SHA-1 should not be relied upon for collision-resistant security applications.

    5. Weak randomness

    Predictable tokens, keys or nonces can undermine cryptographic protection.

    6. Poor key management

    Keys stored in source code, exposed logs, accessible files or poorly controlled systems can defeat encryption.

    Defenses

    Purpose Recommended approach
    Transport security TLS 1.2 or TLS 1.3
    Password storage Argon2id; bcrypt or scrypt where appropriate
    Authenticated encryption AES-GCM or ChaCha20-Poly1305
    Random tokens Cryptographically secure random generator
    Key management Appropriate KMS/HSM and access controls
    Secret storage Protected secret manager; avoid hardcoding
    Certificate security Validate certificate chains and hostnames
    Data at rest Encrypt sensitive data and backups as appropriate

    Password hashing vs encryption

    • Encryption: Reversible with the appropriate key.
    • Password hashing: Designed to be one-way; verification is performed against the stored hash and parameters.

    Password storage should use a purpose-built password hashing algorithm with appropriate parameters and salts—not plaintext, reversible encryption, or a fast general-purpose hash.

    Key takeaway: Encryption is only as strong as its algorithm, implementation, randomness and key management.

    A05 — Injection

    What it is

    Injection occurs when untrusted input is interpreted as part of a command, query or executable language rather than being handled strictly as data.

    Examples include SQL, OS command, LDAP, NoSQL and other forms of injection, as well as XSS.

    1. SQL injection (SQLi)

    A vulnerable application constructs SQL using string concatenation.

    Vulnerable example:

    const query =
  "SELECT * FROM users WHERE username = '" +
  username +
  "' AND password = '" +
  password +
  "'";

    If input is inserted directly into SQL, specially crafted input can change the query's structure or logic.

    The underlying issue is that the database receives a query in which untrusted input has become SQL syntax.

    Defense:

    • Use parameterized queries / prepared statements.
    • Avoid building SQL through string concatenation.
    • Validate inputs according to their expected type and format.
    • Use least-privileged database accounts.
    • Avoid relying on escaping as the primary protection.

    Parameterized query example:

    const query = "SELECT * FROM users WHERE username = ?";
db.execute(query, [username]);

    2. Cross-Site Scripting (XSS)

    XSS occurs when attacker-controlled content is included in a webpage in a context where the browser interprets it as executable script or otherwise unsafe content.

    Stored XSS

    Malicious content is stored (e.g., in a comment) and later rendered to other users.

    Reflected XSS

    Input from a request is reflected into the response without appropriate handling.

    DOM-based XSS

    Unsafe client-side JavaScript manipulates the DOM using attacker-controlled data.

    Defense:

    • Use context-aware output encoding.
    • Use safe DOM APIs (e.g., textContent for plain text).
    • Avoid unsafe HTML insertion such as innerHTML with untrusted data.
    • Use framework escaping correctly.
    • Apply CSP as an additional defense—not a substitute for safe rendering.

    3. OS command injection

    A program constructs shell commands using untrusted input.

    If the input can introduce shell operators or other syntax, an attacker may cause unintended commands to execute.

    Defense:

    • Avoid shell invocation when a direct API is available.
    • Use process APIs that pass arguments separately rather than constructing shell strings.
    • Strictly validate input against expected values.
    • Run processes with minimal privileges.

    General injection defenses

    • Separate data from executable instructions.
    • Validate input, but do not rely on validation alone.
    • Use safe APIs and parameterization.
    • Encode output in the correct context.
    • Apply least privilege.

    Key takeaway: Prevent untrusted input from altering the structure of commands, queries or executable content.

    A06 — Insecure Design

    What it is

    Insecure Design refers to weaknesses in security requirements, architecture, workflows or business logic. The application may be implemented exactly as designed, but the design itself fails to account for security.

    Common forms

    1. Business logic abuse

    An application trusts a client-submitted price instead of calculating the price on the server.

    The attacker manipulates the value to pay less than the intended amount.

    2. Coupon abuse

    The design does not adequately enforce one-time coupon use. Concurrent requests may redeem a coupon multiple times if the check and update are not performed safely.

    3. Insecure account recovery

    Account recovery relies on easily guessed or publicly available information.

    4. Unrestricted upload design

    The design does not properly constrain uploaded content, size, storage, permissions or execution.

    Defenses

    • Perform threat modeling during design.
    • Define security requirements alongside functional requirements.
    • Identify assets, trust boundaries, attack surfaces and abuse cases.
    • Use secure design patterns and secure defaults.
    • Enforce business rules on the server.
    • Never trust client-submitted prices, permissions or transaction state.
    • Use database transactions and atomic operations for sensitive workflows.
    • Set limits on uploads, requests, processing and resource consumption.
    • Design account recovery, authentication and authorization securely.
    • Test abuse cases—not just expected use cases.

    Threat modeling

    Threat modeling systematically identifies:

    1. Assets to protect.
    2. Potential attackers.
    3. Trust boundaries and entry points.
    4. Threats and abuse scenarios.
    5. Security controls and mitigations.

    Example:

    Asset Threat
    Account Account takeover
    Balance Unauthorized modification
    Transactions Fraud
    Customer information Data disclosure

    Key takeaway: Secure implementation cannot compensate for a fundamentally insecure design.

    A07 — Authentication Failures

    What it is

    Authentication Failures occur when identity verification or authentication-related mechanisms are inadequately implemented or protected.

    Common forms

    1. Brute-force attacks

    An attacker repeatedly tries password combinations against an account.

    2. Credential stuffing

    An attacker uses credentials leaked from other services, exploiting password reuse.

    3. Password spraying

    An attacker tries a small number of common passwords across many accounts.

    4. Session fixation

    An attacker causes a victim to use a session identifier known to the attacker. If the application fails to regenerate the session identifier after authentication, the attacker may be able to abuse the authenticated session.

    5. Insecure account recovery

    Weak recovery mechanisms may allow attackers to reset another user's password.

    Defenses

    • Enforce reasonable password length and block common or compromised passwords.
    • Implement login rate limiting and abuse detection.
    • Use MFA; prefer phishing-resistant methods such as FIDO2/WebAuthn when feasible.
    • Store passwords using a suitable password hashing algorithm.
    • Use cryptographically secure session IDs.
    • Regenerate session IDs after authentication and privilege changes.
    • Invalidate sessions on logout and when appropriate after security-sensitive events.
    • Set cookie attributes such as Secure, HttpOnly and appropriate SameSite.
    • Use secure password-reset tokens: random, short-lived and single-use.
    • Monitor suspicious login activity.

    Example cookie:

    Set-Cookie: session=...; Secure; HttpOnly; SameSite=Lax

    Authentication vs authorization

    Authentication Authorization
    Verifies identity Verifies permissions
    Who are you? What can you do?
    Passwords, MFA, certificates Roles, policies, ownership
    OWASP A07 OWASP A01

    Key takeaway: A user may be correctly authenticated but still be unauthorized to access a particular resource.

    A08 — Software or Data Integrity Failures

    What it is

    This category concerns failures to adequately verify the integrity or authenticity of software, code or data that an application trusts.

    Common forms

    1. Insecure software updates

    An application downloads and installs updates without adequately verifying their authenticity and integrity.

    An attacker who can alter the update may supply malicious software.

    2. Insecure deserialization

    An application reconstructs objects from untrusted serialized data without appropriate validation or safeguards.

    Depending on the technology and implementation, this can enable manipulation of application state, dangerous behavior or code execution.

    3. Artifact tampering

    An attacker modifies software artifacts between build and deployment because the pipeline does not adequately protect or verify them.

    Defenses

    • Verify update signatures before installation.
    • Use trusted signing keys and protect private keys.
    • Verify integrity and provenance of artifacts.
    • Avoid deserializing untrusted native objects where possible.
    • Validate serialized input and use strict schemas.
    • Protect CI/CD and artifact storage.
    • Restrict permissions on build and deployment systems.
    • Use immutable or controlled artifacts through deployment.

    A03 vs A08

    A03 — Software Supply Chain Failures A08 — Software or Data Integrity Failures
    Broad focus on software ecosystem and production/distribution chain Focus on trust and integrity verification
    Vulnerable or malicious dependencies Unverified updates
    Compromised development tools Tampered artifacts
    Compromised repositories or pipeline Unsafe deserialization or missing verification

    These categories may overlap in real attacks.

    Key takeaway: Do not trust software or data solely because it came from a source you normally use; verify it appropriately.

    A09 — Security Logging and Alerting Failures

    What it is

    Security Logging and Alerting Failures occur when security-relevant events are inadequately recorded, monitored, analyzed or reported.

    Logging helps establish what happened; monitoring analyzes activity; alerting notifies responders.

    Common forms

    1. Failed logins not recorded

    Repeated authentication failures may go unnoticed, preventing detection of brute-force activity.

    2. No alerts

    An application records suspicious activity but does not alert anyone or any system capable of responding.

    3. Log tampering

    Logs stored on a compromised system may be altered or deleted.

    4. Sensitive data in logs

    Passwords, tokens, session identifiers or sensitive information may be exposed through logs.

    5. Log injection

    Untrusted input is recorded in a way that can create misleading entries or interfere with analysis.

    Defenses

    • Log security-relevant events:
    • Login success and failure
    • Password and account changes
    • Authorization failures
    • Administrative actions
    • Sensitive data access
    • Configuration changes
    • Security-sensitive transactions
    • Centralize logs.
    • Restrict access to log data.
    • Protect logs against modification and deletion.
    • Alert on suspicious patterns.
    • Sanitize untrusted data before logging.
    • Do not log passwords, secrets, tokens or session identifiers.
    • Establish retention and incident-response procedures.

    Examples of log and monitoring platforms include SIEM systems, ELK Stack, Splunk and Graylog.

    Logging vs monitoring vs alerting

    Term Meaning
    Logging Recording events
    Monitoring Observing and analyzing events
    Alerting Notifying someone or a system of suspicious activity

    Key takeaway: Prevention is not enough. Security events must also be detectable and investigated.

    A10 — Mishandling of Exceptional Conditions

    What it is

    A new category in the OWASP Top 10:2025, focusing on insecure handling of unexpected failures, abnormal conditions and execution states.

    Poor exception and failure handling may result in information disclosure, denial of service, inconsistent state or security-control bypasses.

    Common forms

    1. Fail open

    A security check fails, but the application grants access or permits an operation.

    Example: An authorization service is unavailable, and the application assumes permission is granted.

    2. Information disclosure

    Detailed error messages expose internal paths, database details, stack traces, configuration or other sensitive information.

    3. Null pointer dereference

    An unexpected null value is dereferenced, potentially causing a crash or undefined behavior.

    4. Missing or invalid parameters

    An application fails to handle missing, malformed or unexpected input correctly.

    5. Improper exception handling

    An exception is caught incorrectly, ignored, or followed by unsafe execution.

    6. Inconsistent state

    A failed multi-step operation leaves data partially updated, such as debiting an account without crediting the destination account.

    Defenses

    • Fail securely (fail closed for security-sensitive checks).
    • Use centralized and consistent exception handling.
    • Validate input types, ranges, required parameters and state.
    • Avoid exposing detailed internal errors to clients.
    • Log detailed diagnostics securely.
    • Handle timeouts, resource exhaustion and service failures.
    • Use database transactions for multi-step operations.
    • Use safe resource-management techniques such as RAII in C++.
    • Test failure scenarios, not just normal execution.

    Fail open vs fail closed

    Fail open: A failure allows the operation or grants access.

    Fail closed: A failure denies the operation or access.

    For security-sensitive operations, failing closed is generally safer.

    Example:

    Authorization service unavailable
        |
        v
Cannot verify permission
        |
        v
Deny access

    Key takeaway: An application must remain secure when things go wrong, not only when everything works.

    Comparison of the 10 categories

    Category Core issue
    A01 — Broken Access Control Users can perform unauthorized actions or access resources
    A02 — Security Misconfiguration Insecure settings, deployment or configuration
    A03 — Software Supply Chain Failures Compromised or vulnerable software ecosystem and delivery chain
    A04 — Cryptographic Failures Sensitive data inadequately protected by cryptography
    A05 — Injection Untrusted input alters commands, queries or executable content
    A06 — Insecure Design Security weaknesses in architecture, requirements or business logic
    A07 — Authentication Failures Identity verification or authentication mechanisms are weak
    A08 — Software or Data Integrity Failures Software or data is trusted without adequate integrity/authenticity verification
    A09 — Security Logging and Alerting Failures Security events are inadequately recorded, monitored or reported
    A10 — Mishandling of Exceptional Conditions Unexpected failures or abnormal conditions are handled insecurely

    Frequently confused categories

    Pair Difference
    A01 vs A07 A01 is about permissions; A07 is about identity verification
    A02 vs A06 A02 is insecure configuration; A06 is insecure design
    A03 vs A08 A03 is the broader supply chain; A08 is trust and integrity verification
    A04 vs A08 A04 is cryptographic protection; A08 is integrity/authenticity of software or data
    A05 vs A06 A05 is input interpreted as instructions; A06 is fundamentally insecure architecture or business logic
    A09 vs A10 A09 is logging, monitoring and alerting; A10 is handling unexpected execution conditions

    Interview revision — Concepts to prioritize

    Priority Concepts Category
    Very high IDOR, horizontal/vertical escalation, CSRF A01
    Very high SQLi, XSS, command injection A05
    Very high Brute force, credential stuffing, session fixation A07
    High Hashing vs encryption, salts, key management A04
    High Threat modeling and business logic vulnerabilities A06
    High Dependency confusion, SBOM, CI/CD security A03
    High Fail open vs fail closed A10
    Medium Debug mode, directory listing, secure headers A02
    Medium Digital signatures, insecure deserialization A08
    Medium SIEM, centralized logs, log injection A09

    Core mechanisms to understand

    • SQL injection: Input changes the structure of a SQL query.
    • IDOR: The server fails to verify permission for a requested resource.
    • CSRF: A browser may automatically send authentication cookies with a forged request.
    • Session fixation: A session identifier is not properly regenerated.
    • Insecure deserialization: Untrusted serialized data is reconstructed unsafely.
    • Fail open: A security check fails but access or an operation is allowed.
    • Credential stuffing: Previously leaked credentials are reused against another service.
    • XSS: Attacker-controlled content is interpreted as executable browser content.

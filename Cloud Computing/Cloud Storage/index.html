    Cloud Storage

    Cloud Storage Options

    • Relational Databases - RDBMS with strong consistency. Traditional storage option, but harder to scale, lower performance.
    • No-SQL data storage - Map key to unstructured blob of data. Simpler get/put operations using key and no transaction support. Higher performance.
    • Semi-structured data storage - map key to value which contain column families, but not fixed schema.

    Examples

    • Dynamo - High performance No-SQL key value from Amazon. High availability and scalability
    • Bigtable - Semi-structured data storage used at Google. Built over Google Chubby (a distributed locking/consensus system) and Google File System (a distributed file system).
    • Haystack - Cloud storage system for efficiently storing and retrieving photos at Meta.
    • Memcache - A distributed cache used at Facebook to cache queries from database servers.

    Amazon Dynamo

    • A distributed key-value store. Simple get/put interface.
    • High availability.
    • Eventual consistency over strong consistency. The updates happen asynchronously.
    • No ACID properties to prioritise latency and availability → (CAP theorem).

    Architecture

    • A service chain of web servers.
    • Aggregator services aggregate data from multiple applications.

    Data versioning using Vector Clocks

    • Vector clock is a metadata indicating multiple versions of a data.
    • Set of (node, count) pairs, incremented locally at every node.
    • Version clock version number associated with value (context) is returned with every get to the client, and the client sends it along with its next put request.

    Partitioning and Replica

    • Consistent Hashing
    • Hashes the data item into a key, and finds the node to store it using the position → Successor node
    • Removing / Adding a node would change hashing elements.
    • Issues due to basic consistent hashing resolved by Virtual Nodes
    • Put operation writes to subset W of N nodes and Get operation retrieves from subset R of N nodes. W, R and N are chosen such that R + W > N, so that the latest value can be retrieved most of the times. (Quorum Protocol)

    Failures and Eventual Consistency

    • Node/Network Failures - Finds first N alive nodes (Sloppy quorum). Nodes in original preference list will be contacted and updated when they come back.
    • Asynchronous - Coordinator does not wait for confirmation from all W nodes before sending a reply to the client.
    • A get after put can find multiple versions at different nodes.
    • Hinted handoff - If a node is not available, another node temporarily stores it. When the node comes back online, the data stored in the interim node is transferred.

    Permanent Failures

    • The nodes may have inconsistent data between replicas.
    • A Merkle tree is a tree in which every leaf contains a hash of some data, and every internal nodes contains a has computed from its children’s hashes.

    • Hashes will differ when there are inconsistencies, recursively find the nodes to be repaired.
    • log2(n) operation

    Membership and Failure Detection

    • Each node periodically exchanges membership information with other nodes.
    • Failure information propagated to other nodes sequentially.

    Google’s BigTable

    • Semi-structured data store
    • Tables of rows, columns (strings). Each cell also has a timestamp. Maps row key, column key and timestamp to a value (array of bytes).
    • (row, column, timestamp) → string
    • High availability, scalability and performance

    Data Model

    • Rows: atomic unit of reading and writing data
      • Rows sorted alphabetically
      • Group of adjacent rows is called tablet.

    • Columns: Group into a small of families

      • All columns in a family store similar type of data, treated similarly

    • Timestamp: Acts as version number, provided by clients

      • Last N versions stored

    Building Blocks

    • Uses SSTable and Chubby
    SSTable (Sorted String Table)

    • Immutable file-based data structure
    • Can lookup a value with single disk access - first index and then access the data block
    • Lookup only needs single disk access
    • No need of locks during reads and writes due to immutability
    Google File System
    • Distributed file system
    • Efficiently store a small number of large files
    • GFS cluster has one master and multiple chunk servers
    • File divided into fixed size chunks, chunks replicated
    • Chunks identified by a unique handle
    • Master stores chunk hand → chunk server mapping

    Chubby
    • Distributed lock service
    • Users of chubby can acquire a lock on some directory / file and read / write its contents
    • The node that acquires the lock is the master and shares the data with replicas using Chubby files
    • Chubby implements Paxos across its 5 replicas
    • Clients maintains sessions with Chubby servers and send requests to acquire / release locks

    Implementation

    Components

    • Tablet servers - Store few hundred tablets
    • Master - Distributes tablets to tablet servers, load balancing, handles failures of tablet, creation / updation of table schema
    • Clients - Read / write tablets at tablet servers
    Tracking Tablet Servers
    • Every tablet server create its own unique file on chubby
    • Master periodically looks at these files to find a list of healthy tablet servers, assigns each tablet to one tablet server
    • If the tablet server fails, Chubby connection is lost, file is deleted and master assigns its tablets to other servers
    • If master fails, it scans list of tablet servers, queries them for tablets, and reconstructs tablet assignment
    Locating Tablets

    • Tablet locations stored in metadata
    • Locations of all metadata tablets stored in root tablet
    • Root tablet published in Chubby by master
    • Clients cache locations of tablets
    Write Operation
    • Changes first written commit logs on GFS
    • Recently committed writes are in MemTable
    • Old data is not deleted from SSTable, only deletion record written
    Read Operation
    • Reads the latest one from MemTable and SSTable using timestamp

    Facebook Haystack

    Why not store photos as regular files

    • Many attributes permissions are meaningless
    • Lot of metadata accesses (inodes) before actual photo access
    • App specific knowledge: photos are written once, read often, rarely modified
    • High throughput, low latency required

    Typical design of photo/object storage

    • Photos and read only objects served by CDN
    • CDN caches such objects
    • CDN improves performance for only popular photos, unpopular photos receive significant amount of traffic

    NFS-based photo storage

    • Each photo stored as a seperate file on Network Attached Storage (NFS filesystem)
    • Atleast three disk access (Parent Block → Inode Block → Data Block)
    • Motivation - Reduce the size of metadata per photo, so that all metadata in memory and one disk access per photo

    Haystack Architecture

    • Store, Cache and Directory
    • Store - Has the actual photos (Machine)
    • Cache - Caches popular content that is not already cached in CDNs
    • Directory - Maintains location mapping (which CDN/cache/store/logical volume may have the photo)
      • Directory returns URL encoded with location of the photo: CDN/cache/store/logical volume
      • Can check in CDN first, or directly go to cache
    Photo Upload

    • Photo goes to webserver
    • Directory returns the location of the store server and logical volume where photo to be stored
    • A logical volume is replicated at multiple physical volumes
    Store Server Architecture
    • Each store server has multiple physical volumes
    • Physical volume is a large file that belongs to one of the logical volumes
    • Logical volume → collection of different physical volumes on different servers
    • Directory has all info on physical and logical volumes on all store volumes
    • New machine added to store: write enabled
      • Once capacity is full, moves to read-only mode
    Disk Layout
    • Each physical volume has a superblock and a set of needles
    • Needle - photo + all its metadata
    • Large file stored on disk using existing filesystems
    In-Memory data structure
    • Store server has file descriptor for each physical volume
    • In-memory index maps photo to offset within disk
    • New photo → Append to the physical volume → update index
    • Modification → New copy appended at end, index updated to point to latest version
    • Old data not overwritten, periodic compaction is done to delete stale entries
    Updating Index File
    • In memory
    • Index file written to disk asynchronously after appending actual data to disk
    • If system crashes after updating data before updating index, index file on disk may be stale
    • During bootup, start with index file, see latest entry in index, all disk records are read

    Memcache

    • Demand filled look-aside cache
    • Web server reads the data → Looks up cache → if cache miss → populate the cache
    • Web server writes data → write directly to backend → invalidates cache data
    • Used for read-heavy workloads

    Overall Architecture

    • Frontend clusters
      • Web server (memcached clients)
      • Memcache (memcached servers)
    • Backend storage clusters
      • MySQL databases
    • Frontend and Backend clusters arranged into regions
    • Keys divided between memcached servers by consistent hashing
    • Web servers contact the memcached server via library (Get → UDP, Put → TCP)

    Handling stale values in cache

    • In the case above, there will be inconsistent data stored in cache.

    • When C1 puts value V1 in database, it gets a lease number (64 bit version number)
    • C2 also gets a lease with a higher sequence number
    • C1’s put wont be accepted as the older lease is gone.

    Avoiding the thundering herd

    Suppose we have: - A database service - A cache server - Multiple clients C0, C1, C2….Cn

    • We update the data, the value in the cache is invalidated
    • All 100 clients discover that cache does not have the value
    • All requests reach the backend even though they are requesting the same key → Sudden spike
    • Solution: Leases
    • Lease is a temporary permission by backend to a particular client to fetch and populate the cache
    • C1 gets the lease and populates the cache, others fetch the value from cache
    • Alternatively, allow clients to use the stale value in cache, but temporary inconsistency

    Server pools

    • Suppose there are two types of keys
      • Type A: Long-lived keys that rarely changes
      • Type B: Short-lived keys that change frequently
    • Solution: Seperate pools, no fear of Type A key eviction

    • What happens when a cache server fails?
    • Approach A: Remap keys to another server
    • But if a frequently used key is remapped, it may overload the system as it has to handle the existing workload as well. Also remapping can cause spikes in load
    • Approach B: Gutter pool
    • Memcached uses a seperate set of temporary servers called Gutter pool
    • Client C1 requests K1 → K1 was supposed to be in S2 → S2 is not available → C1 gets the value from database and populates S4 (Gutter pool).

    Handing Server Overload

    • Solution 1: Add another server and give away some keys to new server

      • Multiget operations may require data from both the servers. In this case, both servers will get multiple requests but lesser number of keys in each request
      • Solution 2: Replication
      • Replication is better than splitting key space when a lot of keys requested together in multiget

    Single Memcached server optimisations

    • Memcached stores key value pairs in a hash table with fixed size.
      • Too many keys can accumulate in the same bucket (collision)
      • In this case, the hash table is expanded, keys are rehashed and constant lookup time is achieved
    • Make the server multi-threaded
      • Use fine grained locking (not the entire hash tables, just buckets maybe)
    • Each thread has a UDP port to avoid contention
    • Slab allocators of various sizes to reduce dynamic memory allocation (repeated malloc() and dealloc())
    • Proactively remove short lived keys instead of depending on LRU algorithm. Short lived keys can be stored in separate cache item

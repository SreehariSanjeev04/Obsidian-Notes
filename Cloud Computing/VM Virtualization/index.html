    VM Virtualization

    Trap and Emulate

    • All CPU have multiple privilege levels → Rings 0,1,2,3 in x86
    • User process in ring 3, OS in ring 0
    • Situation A - System Call → Trap reaches VMM → Transferred to Guest OS → Handled by Guest OS
    • Situation B - Privileged Operation → reaches Guest OS → Emulated by VMM
    • Sensitive data structures like IDT are managed by VMM, not guest O

    Problems

    • Guest OS may realize that it is not running at the current level.
    • Some x86 instructions which change hardware state run in both privileged and unprivileged modes, leading to different behaviour
    • OSes were not developed to run at a lower privileged level
    Example
    • EFLAGS register is a set of CPU flags (IF interrupt flag indicates if interrupts on/off)
    • POPF instruction pops values on top of stack and set eflags
    • If executed in ring 1, only some flags are set (IF flag is not set as it is privileged)
    • Essentially, trap is not produced

    Popek Goldberg Theorem

    • Sensitive Instruction - changes hardware state
    • Privileged Instruction - Runs only in privileged mode
    • In order to build a VMM via trap and emulate method, sensitive instructions should be a subset of privileged instructions. For x86, this is not possible

    Techniques to virtualize x86

    • Hardware assisted virtualization: KVM/QEMU in linux

      • CPU has a special VMX mode of execution
      • x86 has 4 rings on non-VMX root mode, and another 4 rings in VMX mode
      • VMM enters VMX mode to run guest OS in ring 0
      • Exits back to VMM on triggers (VMM retain control)

    • Paravirtualization - Rewrite guest OS code to be virtualizable

      • Guest OS wont invoke privileged operations, rather make hypercalls
      • Need OS source code changes
      • Example - Xen hypervisor
    • Full Virtualization - CPU instructions of guest OS are translated to be virtualizable
      • Sensitive instructions are translated to trap to VMM
      • Dynamic binary translation
      • Higher overhead than paravirtualization
      • Example - VMWare Workstation

    Memory Virtualization

    Techniques for memory virtualisation

    • Shadow Paging - VMM creates a combined mapping GVA → HPA and MMU is given a pointer to this page table. VMM tracks changes to guest page table and updates shadow page table

    • Extended Page Table - MMU hardware is aware of virtualization and takes two pointers and performs an address translation walk.

    I/O Virtualization

    • Emulation - Guest OS I/O operations trap to VMM, emulated by doing I/O in VMM or host OS
    • Direct I/O or device passthrough - Assign a slice of a device directly to each VM

    Hardware-assisted Virtualization

    • Intel VT-X or AMD-V support
    • Special CPU mode of operation called VMX mode for running VMs
    • QEMU/KVM uses it

    Libvirt and QEMU/KVM

    • Set of tools to manager hypervisors
    • Daemon runs on the system and communicates with hypervisor
    • Exposes an API using which hypervisors can be managed

    QEMU Architecture

    - Userspace process - QEMU talks to KVM via open/ioctl system calls - Allocates memory via mmap - Creates one thread for each virtual CU - Multiple file descriptors to /dev/kvm

    open(/dev/kvm)
ioctl(qemu_fd, KVM_CREATE_VM)
ioctl(vm_fd, KVM_CREATE_VCPU)
for(;;) { //each VCPU runs this loop
    ioctl(vcpu_fd, KVM_RUN)
    switch(exit_reason) {
    case KVM_EXIT_IO: //do I/O
    case KVM_EXIT_HLT:
    }
}

    VMX mode

    • Special CPU instruction to enter and exit VMX mode
      • VMLAUNCH, VMRESUME invoked by KVM to enter VMX mode
      • VMEXIT invoked by guest OS to exit VMX mode
    • VMCS (VM control structure) and VMCB (VM Control block) used to store the CPU context during mode switch
    • When KVM launches a VM, all the host OS execution is suspended

    VM Control Switch (VMCS)

    • Common memory accessible in both modes
    • One VMCS per VM
    • Host CPU context, Guest CPU context, Guest entry / execution / exit control area and Exit information are stored
    • VMCS information exchanged with QEMU via kvm_run structure
    • VMX mode execution mimics the trap and emulate with hardware support
    • QEMU accesses VMCS information using kvm_run

    Traditional Software Virtualisation

    • VMM context - VMM occupies top 4 MB of address space
    • Memory page containing code/data of world switch mapped in both contexts
    • Segmentation used to protected VMM from guest
    Feature Traditional VMM KVM (Intel VT-x)
    Context storage Common cross page Hardware-managed VMCS
    Guest kernel privilege Ring 1 Ring 0, VMX non-root
    VMM privilege Ring 0 Ring 0, VMX root
    VMM location Mapped in guest address space Host kernel, outside guest address space
    Trap mechanism Trap to VMM VM exit to KVM
    Switching mechanism Software world switch Hardware-assisted VM entry/exit

    Binary Translation

    • Guest OS binary translated instruction by instruction and stored in translation cache (to prevent retranslation)
    • Part of VMM memory
    • Privileged OS code traps to VMM

    Dynamic Binary Translation

    • To run privileged operations by Guest OS at Ring 1
    • Translates guest code one basic block at a time to produce a Compiled Code Fragment
    • Once CCF is created, move to ring 1 to run translated code
    • If next CCF in TC, then jump to it

    GS Segment

    • VMM stores register values, control flags, execution flags for both emulation and world switch
    • Translated guest code may need to access VMM data structures like saved register values, program counters, etc.
    • In such cases, memory accesses are rewritten to use the GS segment.
    • GS register points to this space

    Memory Reclamation Techniques

    • VMM reclaims memory from guest RAM under memory pressure
    • Uncooperative swapping - VMM reclaims some guest RAM and swaps them to disk → Guest can page fault
    • Ballooning - VMM opens dummy device, requests pages from VM, then swap these pages
    • Memory Sharing - Memory page with identical content across VMs are shared

    Communication Between OS and Device

    • Device memory is exposed as registers
    • Explicit I/O - IN/OUT instructions in x86 can write to device memory
    • Memory Mapped I/O - Memory addresses are assigned to device memory
    • Device raises interrupt when I/O completes

    • Completely bypasses the Step 3 of I/O handling in KVM struct kvm_run

    Device Passthrough or Direct I/O

    • More efficient than device emulation

    • SR-IOV (Single Root IO Virtualization) in network devices

      • Network card has one Physical Function (PF) and Virtual Functions (VF)
      • PF managed by host OS and VF managed by guest VM
      • Packets are transferred directly into guest VM memory, host OS is not involved

    • Issue - If the Guest OS wants to send or receive packets, it uses Guest Physical Address, which is not understood by physical address.

    • SR-IOV capable NICs have an inbuilt MMU (IOMMU) to translate from GPA to HPA

    Xen and Paravirtualization

    • Xen - Paravirtualized VMM
    • Trap and emulate architecture
    • Xen sits in the top of 64 MB of address space
    • Guest OS traps to Xen to perform privileged actions

    CPU Virtualizaton in Xen

    • Hypercalls - Guest OS voluntarily invokes Xen to perform privileged ops
    • Asynchronous Event Mechanism - communication from Xen to domain to deliver hardware interrupts and other notifications

    Memory Virtualisation in Xen

    • Copy of Shadow Page Table in guest memory
    • Guest is given read-only access to the mapping
    • When guest needs to update, it makes a hypercall to Xen to update the page table
    • Xen validates updates and applies them
    • Segment descriptor tables also maintained similarly

    I/O Virtualisation

    • Shared memory between guest domain and Xen

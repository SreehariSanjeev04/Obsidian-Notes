    1. Why does DNS have security issues?

    DNS translates human-readable domain names into IP addresses.

    For example:

    www.example.com → 192.168.1.10

    However, the original DNS protocol was designed without strong authentication and integrity verification.

    This creates two fundamental problems:

    • Authenticity: How can a client verify that a DNS response actually came from a legitimate DNS server?

    • Integrity: How can a client verify that the DNS information has not been modified?

    DNS is also a public distributed database. Restricting who can query DNS records is generally outside the original protocol's scope.

    Consequences: Attackers can inject false DNS information, redirect users to malicious systems, disrupt name resolution or impersonate trusted hosts.

    The ODT source identifies five major DNS vulnerabilities:

    1. Cache poisoning

    2. Client flooding

    3. DNS Dynamic Update vulnerabilities

    4. Information leakage

    5. Compromise of authoritative DNS data

    2. Cache Poisoning (DNS Spoofing)

    Definition: Cache poisoning occurs when an attacker causes a DNS server to store incorrect DNS information in its cache.

    Normally, when a DNS server receives a query:

    1. It checks its cache.

    2. If the answer is unavailable, it queries another DNS server.

    3. It receives the response.

    4. It caches the received information.

    5. It returns the answer to the client.

    The vulnerability arises when the DNS server accepts incorrect or malicious information from another server.

    How does cache poisoning happen?

    Consider the following example from the ODT document (Figure 5, page 8).

    • host1 requests the IP address of example.org.

    • Its configured DNS server, ourdns.example.com, does not have the answer.

    • It queries brokendns.example.org.

    • The latter returns incorrect DNS information.

    • ourdns.example.com accepts and caches the incorrect information.

    • It sends the false IP address to the client.

    Important: The poisoned information remains in the cache until it expires or is removed. Therefore, subsequent clients using that DNS server may also receive the incorrect address.

    Why were older DNS implementations vulnerable?

    The ODT source identifies two problems in earlier BIND implementations:

    • Additional records in DNS responses were accepted without sufficiently checking whether they were relevant or authoritative.

    • There was no adequate mechanism to ensure that the received answer was related to the original question.

    This allowed attackers to inject bogus records into DNS caches.

    Objectives of cache poisoning

    There are two major objectives.

    A. Denial of Service (DoS)

    An attacker can:

    • Insert a negative response for a domain that actually exists.

    • Redirect users to a different system that does not provide the required service.

    • Insert a self-referential CNAME record.

    Example:

    foobar.example.org. IN CNAME foobar.example.org.

    This is called a self-referential resource record.

    The document explains that such a record can cause a recursive DNS server to crash when a zone transfer is requested.

    B. Masquerading

    The attacker redirects communication to a system controlled by them.

    Consequences:

    • Interception of communication.

    • Analysis of transmitted information.

    • Modification or corruption of communication.

    • Impersonation of a trusted entity.

    A short TTL can make malicious information disappear quickly, making detection more difficult.

    3. Rogue DNS Servers and Host Name Spoofing

    A rogue DNS server contains untrustworthy DNS information and can facilitate DNS spoofing and host name spoofing.

    Host name spoofing using PTR records

    Remember these two records:

    Record Purpose
    A Maps hostname to IPv4 address
    PTR Maps IP address to hostname

    Normally:

    • Forward lookup: IP address is obtained from hostname.

    • Reverse lookup: hostname is obtained from IP address.

    An attacker can manipulate reverse DNS information by configuring a malicious PTR record.

    Example from the document

    Suppose:

    • victim.example.edu trusts trustme.plain.org.

    • This trust is configured through the .rhosts file.

    • An attacker controls a DNS server authoritative for the relevant reverse DNS zone.

    The attacker configures:

    8.0.16.172.in-addr.arpa. IN PTR trustme.plain.org.

    The attacker then connects from IP address 172.16.0.8.

    The victim performs a reverse DNS lookup and receives:

    172.16.0.8 → trustme.plain.org

    Since the victim trusts that hostname, the attacker may be able to gain access without a password.

    DNS Cross-Checking

    To prevent host name spoofing, the document discusses DNS sanity checking.

    The process:

    1. Perform a reverse lookup (PTR) using the IP address.

    2. Obtain the hostname.

    3. Perform a forward lookup (A) using the returned hostname.

    4. Compare the resulting IP address with the original IP address.

    Example:

    Reverse lookup:
172.16.0.8 → trustme.plain.org

Forward lookup:
trustme.plain.org → 10.8.16.22

    The addresses do not match.

    Therefore, the DNS cross-check fails, indicating possible hostname spoofing.

    The diagram in Figure 7 (page 11) illustrates this mismatch.

    Remember: Forward-confirmed reverse DNS checking helps detect inconsistencies between PTR and A records.

    4. Client Flooding

    Definition: Client flooding occurs when a client sends a DNS query but receives and accepts thousands of DNS responses from an attacker.

    How it works

    1. A client sends a DNS query.

    2. An attacker sends thousands of DNS responses.

    3. The responses appear to originate from the expected DNS server.

    4. The client cannot properly authenticate their origin.

    5. The client accepts malicious responses.

    Root cause: Lack of strong authentication of DNS responses.

    Impact: Attackers can use this technique to facilitate hostname spoofing and mislead applications.

    Cache poisoning vs Client flooding

    Cache poisoning Client flooding
    Targets DNS server cache Targets DNS client
    Injects incorrect records into cache Sends thousands of false responses
    Affects subsequent clients using the poisoned cache Attempts to deceive the querying client
    Exploits insufficient validation of DNS data Exploits lack of response authentication

    5. DNS Dynamic Update Vulnerabilities

    Originally, DNS was designed as a relatively static system.

    • DNS zone information was maintained in zone files.

    • Changes were made on the primary DNS server.

    • Updates were generally performed manually.

    DNS Dynamic Update allows records to be added or deleted dynamically.

    For example, DHCP can use DNS Dynamic Update to automatically add or delete DNS records when hosts join or leave a network.

    What is the vulnerability?

    The Dynamic Update protocol provides mechanisms to control which systems can update DNS records.

    However, the document identifies weaknesses in these access controls.

    An attacker may exploit:

    • IP spoofing of an authorized updating system.

    • Compromise of an authorized system.

    Possible attacks

    1. Denial of Service

    The attacker deletes important DNS records.

    2. Malicious redirection

    The attacker modifies an A record to point to a malicious IP address.

    Example:

    Original:

    www.example.com → 192.168.1.10

    Modified:

    www.example.com → 192.168.1.50

    Now clients may be redirected to the attacker's system.

    Solution: Secure DNS Dynamic Update uses DNSSEC authentication mechanisms to verify that updates are legitimate.

    6. Information Leakage

    DNS can expose information about an organization's internal network.

    A. Zone transfers

    A zone transfer allows a secondary DNS server to obtain zone information from the primary server.

    If improperly accessible, an attacker may obtain:

    • Internal hostnames.

    • Server names.

    • Project names.

    • Information revealing the operating system of machines.

    • Network structure.

    B. DNS enumeration

    Even if zone transfers are blocked, attackers can use DNS tools to query IP addresses individually.

    They can discover:

    • Hostnames associated with IP addresses.

    • Unassigned IP addresses.

    • Internal network naming conventions.

    Why are unassigned IP addresses dangerous?

    Suppose an organization trusts an entire IP network instead of specifying individual trusted hosts.

    An attacker may exploit an unassigned IP address to impersonate a trusted host using IP spoofing.

    Important: Blocking zone transfers alone does not completely prevent DNS information leakage.

    Solution mentioned in the document: Split DNS configuration.

    Split DNS allows organizations to maintain different DNS views for internal and external users.

    7. Compromise of Authoritative DNS Data

    This occurs when an attacker gains administrative privileges on a DNS server and modifies the authoritative zone information.

    For example, an attacker obtains root privileges on a Unix DNS server and modifies its zone files.

    Consequences:

    • Incorrect hostname-to-IP mappings.

    • Redirection to malicious systems.

    • Disruption of legitimate services.

    • Compromise of DNS information for an entire zone.

    Protection mechanisms

    The ODT source recommends:

    1. Use the latest BIND version.

    2. Minimize the number of other services running on the DNS server.

    3. Restrict administrative access.

    4. Employ split DNS technology.

    5. Use DNSSEC to protect the integrity and authenticity of DNS data.

    8. DNSSEC – DNS Security Extensions

    Most important solution

    DNSSEC stands for Domain Name System Security Extensions.

    It was developed by the IETF to address the security weaknesses of the original DNS protocol.

    The primary purpose of DNSSEC is to provide:

    • Authentication.

    • Integrity.

    DNSSEC extends the existing DNS protocol using additional Resource Record (RR) types.

    It was designed to maintain backward compatibility with DNS implementations that do not support DNSSEC.

    8.1 Three major services provided by DNSSEC

    Service Purpose
    Key Distribution Distributes public keys required for verification
    Data Origin Authentication Verifies that DNS data comes from the legitimate source
    Transaction and Request Authentication Verifies DNS requests and their corresponding responses

    A. Key Distribution

    DNSSEC provides a mechanism to distribute public keys.

    These keys allow DNS resolvers to verify the authenticity of DNS information.

    B. Data Origin Authentication

    This is the core security mechanism of DNSSEC.

    DNSSEC digitally signs Resource Record Sets (RRSets).

    How it works:

    1. The DNS zone owner creates an RRSet.

    2. A cryptographic hash is calculated over the RRSet.

    3. The hash is digitally signed using the private key of the zone.

    4. The DNS response includes the RRSet and its digital signature.

    5. The resolver obtains the corresponding public key.

    6. It verifies the signature and checks the hash.

    If both hash values match:

    • The data has integrity.

    • The origin of the data is authenticated.

    Why is this important?

    An attacker may modify an RRSet, but cannot produce a valid signature without the corresponding private key.

    Therefore, DNSSEC helps prevent cache poisoning and unauthorized modification of DNS data.

    C. Transaction and Request Authentication

    This mechanism authenticates DNS requests and message headers.

    It ensures:

    • The response corresponds to the original query.

    • The response came from the intended server.

    • DNS Dynamic Updates are authenticated.

    It is particularly useful in securing DNS Dynamic Update operations.

    9. DNSSEC Resource Records

    The ODT document identifies four important DNSSEC-related record types.

    Record Purpose
    KEY Stores public keys
    SIG Stores digital signatures for RRSets
    NXT Cryptographically asserts the nonexistence of an RRSet
    CERT Stores public key certificates for use by applications outside DNS

    KEY RR

    • Stores the public key associated with a DNS name.

    • Used to verify signatures of RRSets.

    • A resolver can receive the corresponding KEY RR along with the DNS response.

    SIG RR

    • Contains the digital signature of an RRSet.

    • Used to establish authenticity and integrity.

    • Generated using the private key of the signing authority.

    NXT RR

    • Used to prove that a particular DNS record does not exist.

    • Provides authenticated denial of existence.

    CERT RR

    • Stores public key certificates.

    • These certificates can be used by applications outside DNS.

    • It does not provide additional DNS security functionality itself.

    10. How DNSSEC protects against DNS attacks

    DNS vulnerability DNSSEC protection
    Cache poisoning Data origin authentication
    Client flooding Data origin authentication
    Dynamic update attacks Transaction and request authentication
    Authoritative data modification Digital signatures and private-key protection
    Information leakage Not directly addressed by DNSSEC

    Important limitation: DNSSEC does not solve information leakage because it is primarily an authentication and integrity mechanism, not an access-control mechanism.

    Split DNS is suggested for controlling information exposure.

    11. DNSSEC – Performance and Key Management Issues

    DNSSEC introduces additional cryptographic operations and additional DNS records.

    Performance considerations

    • Signature generation and verification introduce computational overhead.

    • Additional DNS queries may be necessary to retrieve signatures or keys.

    • DNSSEC tries to reduce additional queries by including signatures and keys alongside DNS responses whenever possible.

    • DNS response size can increase because of additional security records.

    If the response exceeds the permitted message size, some additional records may be omitted, and the resolver may need to make further queries.

    Public key retrieval problem

    How does a resolver trust a public key obtained from DNS?

    Consider:

    1. A resolver obtains a public key for a domain.

    2. It needs to verify the signature associated with that key.

    3. To verify that signature, it needs the signing authority's public key.

    4. That public key must also be verified.

    This creates a chain of trust.

    Solution:

    Configure the resolver with a trusted public key, such as the root zone's public key.

    This trusted key acts as the starting point for verifying keys further down the hierarchy.

    Static key configuration: advantages and disadvantages

    Advantages Disadvantages
    Compromise of one zone's private key does not compromise all other zones' keys Does not scale well
    Provides a trusted starting point Every resolver must be updated when a key changes
